# ADR 0024: Opt-in Git-derived last modification

## Status

Accepted (blog compatibility slice: generic metadata).

## Context

The real-world compatibility blog enables Hugo's `enableGitInfo`: article
"Updated" dates in bylines and info panels, JSON-LD `dateModified`, and
sitemap `lastmod` all come from the last commit that touched a file, and the
live commit dates demonstrably differ from front-matter `date` — the behavior
is exercised, not incidental. Signal's `last_modified` was front-matter
`lastmod` only, which no live file sets.

Git metadata requires process execution and repository access. `signal-core`
is pinned free of I/O (ADR 0005), and the model must stay independent of how
a fact was acquired.

## Decision

- **Placement:** acquisition lives in `signal-cli` (`crate::git`), the crate
  that already owns the filesystem boundary. `signal-core` gains only the
  configuration surface (`[git] last_modified = true`) and the normalized
  result (`last_modified` on `ContentEntry`). One `git log` invocation maps
  site-root-relative paths to last-touch author dates (`YYYY-MM-DD`,
  `\x01`-delimited records so dates and paths can never be confused); scope
  is bounded to commits touching the site root, and site roots inside a
  larger repository get their prefix stripped.
- **Precedence:** explicit front-matter `lastmod` always wins; Git fills the
  gap only when the field is absent. Author intent outranks derived history.
- **Advisory semantics:** a missing `git` binary, a site outside a
  repository, or a failing query yields no derived dates and a successful
  build. Git metadata is never mandatory.
- **Determinism:** within a given repository state the mapping is
  deterministic (same commits, same dates). New commits legitimately change
  derived dates; because `last_modified` already participates in entry
  digests, affected pages invalidate through the existing manifest rules
  with no new input kinds.
- **Off by default:** `[git]` absent means Signal never consults Git, so
  builds are unchanged for sites that do not opt in (and golden trees stay
  reproducible without a repository).

## Consequences

- The observable `enableGitInfo` behaviors (updated bylines, JSON-LD
  `dateModified`, sitemap `lastmod`) are reproducible by a site config flag.
- Build reproducibility across time now depends on repository state when the
  flag is on — same property Hugo has; same caveat documented for sites.
- Committing, rebasing, or history rewrites after a build change the next
  build's derived dates; incremental reuse handles this through entry
  digests.
- `GENERATION_BEHAVIOR_VERSION` was bumped (alert ARIA roles, Mermaid source
  fallback, `extra`/`related` context keys, and Git-derived dates all change
  generated bytes for existing sites).

## Deferred

Additional Git facts (author, hash, per-entry `GitInfo` exposure), committer
vs. author date selection, and rename-aware history (`--follow`) if a real
requirement appears.
