# ADR 0019: Generation-behavior identity for reuse compatibility

## Status

Accepted (slice 14B: reuse compatibility; no schema break, no artifact
dependency changes).

## Context

Slice 13 demonstrated that the manifest recorded every semantic input but not
the code that produced the output. Changing Signal's generation logic
(rendering, date formatting, reading time, excerpts, heading anchors, Markdown
transforms, highlighting, RSS/sitemap serialization, search projection,
JSON-LD, default contexts, artifact planning) can change generated bytes while
leaving entries, queries, templates, config, and static digests identical, so
an incremental build would reuse stale artifacts. The existing
`MANIFEST_SCHEMA_VERSION` answers a different question: whether the metadata
can be read, not whether its output is semantically reusable.

## Decision

- Two separate concepts:
  - `MANIFEST_SCHEMA_VERSION` — structural readability. Unchanged at `1`;
    adding the new field is a backward-compatible extension.
  - generation identity — output-semantics compatibility.
- `Manifest.generation: Option<GenerationIdentity>` records:
  - `engine_version`: the Cargo package version of `signal-cli`;
  - `behavior_version`: `GENERATION_BEHAVIOR_VERSION`, a deliberately
    maintained `u32`.
- Every successful build writes `Some(current_generation())`.
- `artifact_reusable` checks `generation_compatible(prev)` **before** any
  per-artifact comparison. It requires an exact match of both parts. A
  mismatch is an invalidation condition, never an error.
- An absent identity (a manifest written before the field existed) is
  treated as incompatible — compatibility is never inferred from the schema
  version. Such manifests remain readable and still drive stale pruning
  (their artifact inventory is valid), but nothing is reused.
- The identity is a build-wide compatibility gate, not an artifact
  dependency: no `InputRef` variant is added, no edge exists between
  artifacts, and nothing about it is persisted in output content or runtime
  statistics.

## Bump policy

`GENERATION_BEHAVIOR_VERSION` must be bumped for any change that can alter
generated bytes without necessarily changing recorded semantic inputs:
rendering behavior, Markdown transformation, heading-anchor generation, date
presentation, reading-time calculation, excerpt rules, RSS/sitemap
serialization, search serialization, JSON-LD structure, default rendering
contexts, output-changing artifact planning, or generated asset behavior.

It must not be bumped for comments, refactors with byte-identical output,
test-only changes, documentation, or output-preserving performance work.

`engine_version` changes automatically with a package release; because it also
gates reuse, a release conservatively invalidates existing caches even when
output is unchanged. This is deliberate: correctness first, reproducibility
second, automatic cleverness never. There is no attempt to hash sources,
`Cargo.lock`, the compiler, or the operating system.

## Consequences

- A previous artifact is reused only when its inputs match **and** it was
  produced by compatible generation behavior.
- Missing, malformed, or mismatched identity causes a safe full rebuild, never
  unsafe reuse or a build failure.
- Clean and incremental builds of the same state remain byte-identical; two
  independent builds produce identical manifests.
- The frozen sample manifest golden changes when the field's value changes
  (package version or behavior version), which is the intended forcing
  function for a deliberate refresh.
