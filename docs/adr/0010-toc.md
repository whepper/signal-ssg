# ADR 0010: Parse-time heading anchors and TOC projection

## Status

Accepted (slice 7: heading anchors + table of contents).

## Context

Heading anchors must appear both in rendered HTML and in the normalized
model (for TOC fragment links), identically. Generating them in two places
— or scraping them out of HTML afterwards — guarantees eventual drift.

## Decision

- One assignment inside `signal-markdown`: a Comrak `HeadingAdapter`
  writes `<hN id="…">` while recording `(level, plain text, id)` in render
  order. The flattened adapter text is the canonical plain text, replacing
  the old line scanner (which leaked raw inline markup into `Heading.text`).
- The anchor algorithm (`anchor_base` + `anchor_unique`) is Signal-owned,
  documented, and unit-tested — not a copy of Comrak internals. Rule:
  Unicode-lowercase, keep alphanumerics/`-`/`_`, whitespace runs to `-`,
  drop the rest, trim edges, empty → `section`, repeats → `-1`, `-2`, ….
  It deliberately differs from `slugify` (taxonomy URL slugs): fragments
  preserve Unicode readability while URL slugs stay ASCII-safe — separate
  concepts, separate functions, each with one call site family.
- `Toc`/`TocItem` live in `signal-core` as a pure projection over
  `&[Heading]`: H1 excluded, H2–H6 nested by level order, no HTML. Entry
  contexts carry `toc` only when non-empty. No min/max-level configuration
  — unjustified by any requirement so far.

## Consequences

- Templates render `href="#{{ item.id }}"` links that resolve by
  construction; heading-free pages omit the TOC key entirely.
- The projection shape (`Toc` over normalized headings) is ready for a
  future search index to consume without touching HTML.

## Deferred

Search, code/diagram/alert components, heading-level configuration if a
site ever needs it.
