# Signal 1.0.0

Signal `1.0.0` is the first stable release. The pipeline, manifest schema,
and CLI contract documented in `ARCHITECTURE.md` are frozen: future 1.x
releases preserve compatibility with them.

Since `0.2.0`, no generation behavior changed (`behavior_version` is still
8; the frozen manifest differs by the engine version only). What changed is
architectural integrity: the commands now share one canonical
pre-execution pipeline, and the properties 0.2.0 implemented are
mechanically guarded against drift.

## What's in this release

- **One canonical pipeline.** `build`, `check`, `serve`, and
  `build --explain` share the same validation semantics
  (`signal-cli::pipeline`): config gates, spec generation, output-path and
  route validation, template loading, then reference validation — before
  any planning, execution, pruning, or manifest persistence.
- **`signal check` validates what `build` requires.** Invalid menus,
  logical output collisions, invalid route prefixes, template failures,
  and broken references are rejected identically by `build`, `check`, and
  `--explain` (pinned by `crates/signal-cli/tests/pipeline.rs`). `check`
  remains read-only: no writes, no pruning, no manifest mutation.
- **`build --explain` validates before planning.** It describes the plan
  for a site that would otherwise pass the build's gates — never a plan
  for a site the build would reject.
- **Guarded input declarations.** A new regression test proves fields
  outside the entry digest cannot affect resolved bytes, so consuming one
  without digest coverage fails loudly instead of serving stale reuse.
- **Deterministic, explainable incremental builds** (unchanged, now
  frozen): content-hash reuse, per-artifact `BuildPlan` decisions with
  reason codes, `previous manifest − current plan` pruning, atomic
  manifest replacement.
- **Structural reference validation** (unchanged, now frozen):
  pre-render, whole-site, fail-closed; external URLs never fetched.
  Documented limits stand: reference-style/autolink forms,
  template-literal URLs, and raw HTML are outside the structured model.
- **Reproducibility evidence.** Same-platform byte identity (output and
  manifest, clean ≡ incremental) plus a CI matrix covering macOS
  filesystems and a non-UTC timezone. Universal cross-platform byte
  identity is explicitly not claimed; see `ARCHITECTURE.md` §11.
- **Deliberate scope boundaries** (unchanged): no plugins, CMS, SSR,
  asset pipeline, image processing, JS bundling, external crawling, async
  builds, or dependency graph. See `ARCHITECTURE.md` §16.

## Not in this release

Same non-goals as `0.2.0`: no CSS/asset pipeline (`static/` is copied
verbatim), no pagination, no i18n, no search UI, no aliases/redirects,
no live reload (serve rebuilds through the production pipeline; refresh
the browser).

## Compatibility

`signal check` passes on the same sites `signal build` accepts, and the
maintainer's reference site still rebuilds with equivalent routes,
content, metadata, feeds, assets, and presentation (see
[the compatibility documentation](../compatibility/blog.md)). This is not
a claim of general Hugo compatibility.

## Upgrading from 0.2.0

Configuration, templates, and content are compatible. The engine version
changed (`0.2.0` → `1.0.0`), so the first build after upgrading performs
a full rebuild and subsequent builds are incremental again. Generation
behavior is unchanged: no output bytes differ for identical inputs.
